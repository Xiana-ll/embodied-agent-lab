## 一、训练阶段（2026 年 7 月）

### 1.1 HuggingFace / GitHub 访问超时

**现象**：`huggingface-cli download` 长连接不断重试后超时；`git clone` 拉 MiniMind 仓库到一半卡住。

**原因**：国内直连 HuggingFace 和 GitHub 的网络不稳定，大文件（数据集 1.2GB）几乎必失败。

**解决**：
- 数据下载改用 **ModelScope CLI**，同源数据走国内节点；
- 代码仓库改用 **ghproxy 镜像** clone。

**教训**：先确认数据能不能下下来，再谈训练。这类问题占掉的时间比调模型参数多得多。

### 1.2 数据版本不匹配

**现象**：用旧版数据集配新代码，训练时字段对不上，报错或静默产生错误的 prompt。

**原因**：MiniMind 迭代快，`mini` 版数据格式和代码版本强绑定。

**解决**：确认使用 **MiniMind-3 最新版本**对应数据集，重新下载。

**教训**：代码和数据的版本永远成对升级，别混用。

### 1.3 Python 依赖冲突

**现象**：按 `requirements.txt` 固定版本安装后，torch 与其他包互相冲突，装完起不来。

**原因**：`requirements.txt` 里的版本锁是作者环境的快照，和云端镜像的 CUDA / Python 版本不一定对得上。

**解决**：**去掉版本锁**，只保留包名，让 pip 自行解析依赖。

**教训**：环境锁版本是为了可复现，但当镜像本身和你不同时，硬锁只会放大冲突。

### 1.4 datasets 库 schema 报错

**现象**：用 `datasets.load_dataset()` 读 v3 数据时报 schema 不一致。

**原因**：v3 数据新增了 `tools` 等字段，`datasets` 的 schema 推断对异构字段不容错。

**解决**：放弃 `datasets`，**改用 Python 原生逐行读取** jsonl，自己拼 batch。

**教训**：数据格式一变，高层封装库反而是负担；底层读取最稳。

## 二、部署阶段（2026 年 10 月 28 日）

### 2.1 `torch_dtype` 参数已弃用

**现象**：

```
python.exe : `torch_dtype` is deprecated! Use `dtype` instead!
```

**原因**：transformers 新版本改了参数名。

**解决**：`AutoModelForCausalLM.from_pretrained(..., torch_dtype=torch.float32)` → `dtype=torch.float32`。

### 2.2 控制台中文全部乱码

**现象**：模型回复在终端里显示成 `ä½ å¥½ï¼ææ¯...`。

**原因**：Python 按 UTF-8 输出，Windows PowerShell 控制台按本地代码页（GBK/Latin-1）解码，两边编码约定不一致。**数据本身是对的，只是显示不对。**

**解决**：
```powershell
$env:PYTHONIOENCODING = "utf-8"
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
```

**教训**：看到乱码先怀疑「显示层」，不要急着怀疑模型。验证方式是把结果写进文件再用 UTF-8 读，而不是盯着终端看。

### 2.3 退出码 1，但命令其实是成功的

**现象**：跑 `check_model.py` 输出正常、模型也回复了，但 PowerShell 报 `[exit code: 1]`。

**原因**：PowerShell 把原生程序写到 **stderr** 的内容（这里是上面那条 deprecation warning）当成错误记录，于是整条管道被判失败。

**解决**：修掉 warning（2.1）之后自然消失；判断成功与否要看**实际输出**，不能只看退出码。

**教训**：非零退出码 ≠ 命令失败。要区分「真报错」和「只是往 stderr 打了日志」。

### 2.4 模型回复里混着 `</think>`

**现象**：接口返回的 content 里带着 `<think>` / `</think>` 标记，而且思考段和正式回答重复出现两遍。

**原因**：MiniMind 会先输出一段思考再给答案，特殊标记没有在解码阶段被过滤。

**解决**：在 `server.py` 里加 `clean()`，用正则 `re.sub(r"<think>.*?</think>", "", text, flags=re.DOTALL)` 剥掉，并兜底清除孤立的 `</think>`。

**教训**：模型输出 ≠ 可直接展示的内容，中间永远需要一层清洗。

### 2.5 服务启动需要等，直接请求会失败

**现象**：`uvicorn` 起来后立刻 curl，连接被拒。

**原因**：模型加载（127MB 权重 + 初始化）要数秒，`/health` 之前端口还没真正 ready。

**解决**：请求前轮询 `/health`（最多 60 次 × 2 秒），而不是固定 `sleep`。

**教训**：启动就绪是异步的，用探针等，不要用固定睡眠赌。

### 2.6 贪心解码导致整段复读

**现象**：`do_sample=False` 时，回复会陷入「能够处理和提供的信息……」的无限重复。

**原因**：64M 小模型在贪心解码下容易掉进局部循环。

**解决**：演示时用 `temperature=0.7`（`do_sample=True`）缓解。这是能力问题，不是 bug。

## 三、Agent 阶段

### 3.1 模型对「你好」也去调用工具

**现象**：问「帮我算一下 256 乘以 37」→ 正确调用 `calculate_math`，结果 9472 ✅
但问「你好」→ 也调用了 `get_current_time` ❌

**原因**：63.9M 参数的模型对「要不要调工具」的判断精度不够，倾向于只要看到工具清单就选一个。

**解决**：**没有用硬编码规则去修**。这是模型能力的真实边界，保留下来作为答辩素材，说明小模型在工具选择上的局限。

**教训**：有些"bug"不该被修掉——修掉就掩盖了模型的真实水平。能讲清边界比假装完美更有说服力。

### 3.2 仓库描述把参数量写成了 128M

**现象**：GitHub 仓库的 Description 写的是「MiniMind 128M 本地模型」。

**原因**：凭印象写的，和实测的 63.91M 不符。

**解决**：网页 Edit repository metadata 改回「63.9M」。

**教训**：凡是写进文档的数字，必须是跑出来的，不能是记得的。

## 四、仍存在的问题（已知边界）

| 问题 | 原因 | 后续 |
|---|---|---|
| 工具选择精度低 | 模型只有 63.9M 参数 | 换更大模型，或用规则前置判断 |
| 无流式输出 | 只实现了非流式接口 | 加 SSE 即可，Agent 用不到 |
| 事实性幻觉 | 信息论上限，参数量不够存知识 | 需 RAG 或更大模型 |

## 五、总结

1. **现象 → 原因 → 解决** 三段式记录，比记「报错截图」有用得多。
2. 训练代码本身不复杂，**大部分时间花在环境、网络、版本兼容上**。
3. 先写冒烟测试（`check_model.py`），把「模型坏了」和「服务坏了」分开，能省掉大量瞎猜。
4. 看到异常先分层定位：是数据、是显示、还是逻辑。
